To make this work, you need to transition from "Copy-Pasting Databases" to **"Evolving Databases."** 

Here is the complete setup: the Controller code, the configuration, and the workflow you need to follow.

### 1. The Migration Controller
This controller allows you to see if the database is out of date and trigger the update via Swagger.

```csharp
using Microsoft.AspNetCore.Mvc;
using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Configuration;
using System;
using System.Collections.Generic;
using System.Linq;
using System.Threading.Tasks;

namespace YourProject.Controllers
{
    [ApiController]
    [Route("api/[controller]")]
    public class DbMaintenanceController : ControllerBase
    {
        private readonly YourDbContext _context;
        private readonly IConfiguration _config;

        public DbMaintenanceController(YourDbContext context, IConfiguration config)
        {
            _context = context;
            _config = config;
        }

        /// <summary>
        /// Shows which migrations are already applied and which are pending.
        /// </summary>
        [HttpGet("status")]
        public async Task<IActionResult> GetStatus([FromHeader(Name = "X-Admin-Key")] string adminKey)
        {
            if (!ValidateKey(adminKey)) return Unauthorized("Invalid Admin Key");

            var applied = await _context.Database.GetAppliedMigrationsAsync();
            var pending = await _context.Database.GetPendingMigrationsAsync();

            return Ok(new
            {
                CurrentDatabase = _context.Database.GetDbConnection().Database,
                AppliedMigrations = applied,
                PendingMigrations = pending,
                IsUpToDate = !pending.Any()
            });
        }

        /// <summary>
        /// Executes the migration to update the database schema.
        /// </summary>
        [HttpPost("migrate")]
        public async Task<IActionResult> RunMigration([FromHeader(Name = "X-Admin-Key")] string adminKey)
        {
            if (!ValidateKey(adminKey)) return Unauthorized("Invalid Admin Key");

            try
            {
                // Increase timeout for long migrations
                _context.Database.SetCommandTimeout(TimeSpan.FromMinutes(5));
                
                // This command executes the SQL scripts generated by EF Core
                await _context.Database.MigrateAsync();

                return Ok("Database migrated successfully.");
            }
            catch (Exception ex)
            {
                // In production, log 'ex' to a file
                return BadRequest($"Migration failed: {ex.Message}");
            }
        }

        private bool ValidateKey(string key)
        {
            var secret = _config["AdminSettings:MigrationKey"];
            return !string.IsNullOrEmpty(key) && key == secret;
        }
    }
}
```

### 2. What else do you need to do? (The Essentials)

The controller is only 50% of the solution. Here are the other "moving parts" you must set up:

#### A. Configure the Connection String per Client
In your `appsettings.json` **on the client's IIS server**, make sure the connection string points to their local SQL instance. Since the API runs on the same server/network as their SQL, it uses a local connection.

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=localhost;Database=Client_A_DB;User Id=sa;Password=YourPassword;"
  },
  "AdminSettings": {
    "MigrationKey": "SuperSecretKey123!"
  }
}
```

#### B. Handle the First-Time Setup
Since you currently "paste" the database, you can stop doing that.
1. Install a blank SQL Server on the client site.
2. In the `appsettings.json`, name the database (e.g., `HR_System_DB`).
3. Run the `migrate` endpoint. **EF Core will automatically create the database and all tables** if the database doesn't exist yet.

#### C. Enable Swagger in Production
By default, ASP.NET Core only shows Swagger in "Development" mode. Since you need to access it on the client's IIS to run the migration, change your `Program.cs`:

```csharp
// Move this OUT of the "if (app.Environment.IsDevelopment())" block
app.UseSwagger();
app.UseSwaggerUI();
```

#### D. Use "Code-First" at your Office
You must change how you work at your office:
1. When you want to add a column (e.g., `Salary`), update your C# Class.
2. Open the Package Manager Console and type: `Add-Migration AddSalaryToEmployee`.
3. This creates a folder in your project called `/Migrations`. **These files must be included in the build you send to the client.**

#### E. Data Seeding (Initial Data)
If you have tables that need default values (like `UserRoles` or `Countries`), don't add them manually in SQL. Add them in your `DbContext.cs`:

```csharp
protected override void OnModelCreating(ModelBuilder modelBuilder)
{
    modelBuilder.Entity<Role>().HasData(
        new Role { Id = 1, Name = "Admin" },
        new Role { Id = 2, Name = "User" }
    );
}
```
When you run the Migration Controller, it will automatically insert these rows if they don't exist.

### 3. Summary of your New Workflow

1.  **Develop:** You change the code and run `Add-Migration` at your office.
2.  **Publish:** You build the C# API and the React app.
3.  **Deploy:** You copy the files to the client's IIS.
4.  **Update Config:** You ensure the client's `appsettings.json` has their specific SQL connection string.
5.  **Migrate:** You open `http://client-server/swagger`, go to the `DbMaintenance` section, put in your secret key, and click **Execute**.
6.  **Verify:** Your React app (CRA) now works perfectly with the updated database.

**Why this wins:** You never have to touch a `.bak` or `.mdf` file again. You never risk deleting the client's data. One codebase fits every client.
